# Cortex schema: a space of personal notes

You maintain this space of the human's own notes: meetings, work notes and docs, daily notes, appointments to remember. The human writes or captures the notes, asks the questions and sets the direction. You do the bookkeeping: turn the notes into linked wiki pages, update, flag contradictions. This file is authoritative. Suggest a change when a convention no longer holds.

> Generated by `cortex` from its built-in notes schema (the `content` of the space, or the file named by `schema` in `cortex.json`). Regenerate it with `cortex schema --write` rather than editing it by hand.

## Absolute rules

1. **`raw/` is immutable.** You read it, you never modify it. Single exception: switching a source's `status` field from `pending` to `compiled`.
2. **You only write inside `wiki/`.** A new note enters `raw/` through `cortex add`, never by hand.
3. **Every factual claim is sourced** with a footnote `[^id]`, where `id` matches an entry of `sources[]`. When you have no source, say so explicitly ("to be checked").
4. **You never write `wiki/index.md` or `wiki/log.md` by hand**: `cortex index` regenerates the first from the frontmatters, and `cortex log add` appends to the journal (`wiki/log.jsonl`), from which `log.md` is generated.
5. **You update before you create.** Look for an existing page first (a person, a project and a client usually have one already), then search. A duplicate is worth less than an enriched page.
6. **You keep the human in the loop.** On every ingest, present what you keep and the pages you intend to touch, then write.
7. Wiki language: **{{language}}**. Quotes and note titles stay in their original language.
<!-- notes:begin -->
8. **The notes are the human's words.** Keep their facts, decisions, dates, names and figures. Do not invent, embellish or guess what a note does not say (write "to be checked"). Do not summarise away a detail that matters later: who, what was decided, by when, how much.
<!-- notes:end -->
9. **No emojis, no pictograms** (check marks, crosses, warning signs) in the pages you write. Express status and structure with plain Markdown.

## Layout

```
cortex.json                  # configuration; marks the wiki root
raw/YYYY/MM/<uuid>/source.md # captured notes (+ assets/); default naming
wiki/index.md                # catalog (OKF reserved, no frontmatter)
wiki/log.jsonl               # append-only journal, source of truth (one JSON entry per line)
wiki/log.md                  # generated from log.jsonl (OKF reserved)
wiki/sources/<uuid>.md       # type: Source: one per raw note (a meeting, a day, an appointment)
wiki/concepts/<uuid>.md      # type: Concept: how something works, a procedure, a how-to
wiki/entities/<uuid>.md      # type: Entity: a person, project, client, place or organization
wiki/syntheses/<uuid>.md     # type: Synthesis: a recurring theme across several notes
```

- **Identifiers: UUID v7 by default**, for raw notes and wiki pages alike (time-ordered then random: unique, no name collision, sorted in creation order). Naming and folder structure are set in `cortex.json` (`raw_path`, `page_path`); the layout above is the default one. You never make up a name: `cortex add` names a note, `cortex new` creates a page, following the configuration. Never write a page into a file that already exists, nor under the file name of another page: the CLI refuses it, and puts back a page replaced by another (other type, title or sources). You find a page by its **title** (index, `cortex search`), not by its file name.
- **A name is final.** A page is never renamed: change its title, its path stays.

## Raw note format (`raw/.../source.md`)

```yaml
---
type: RawSource
title: "Meeting with Acme, weekly sync"
kind: note                    # note (typed or dictated) | pdf | image | audio | article…
content: note                 # note | resource (set by the CLI: what the human wrote, or an outside source)
sha256: …                     # filled in by the CLI
fetched_at: 2026-11-04T09:12:00+01:00   # when it was captured, not when the event happened
extractor: manual
note: "Meeting with Acme"     # optional: the human's intent, when given
status: pending               # pending | compiled | skipped
---
<the note, in Markdown, as the human wrote it>
```

The date of the event is the one the note states (or the human gives), not `fetched_at`. When a note gives none, say so in the page rather than using the capture date as if it were the event's.

The `note` is optional. When it is there, it sets the angle of the Source page. When it is absent, don't ask for it: read the note for what it brings to the wiki as it stands.

## Wiki page format (OKF v0.2 subset)

```yaml
---
type: Source                        # Source | Concept | Entity | Synthesis (the only mandatory field)
title: Weekly sync with Acme, 2026-11-04
description: One sentence, used as is in the index.
tags: [acme, meeting]               # 1 to 4 (max_tags in cortex.json), lowercase, reuse rather than invent
status: draft                       # draft | stable | deprecated
generated: { by: claude-code/opus-5.5, at: 2026-11-04T10:00:00+01:00 }
sources:
  - id: acme-sync-2026-11-04
    resource: /raw/2026/11/01a1a5c9-5e80-7075-ae13-aab03b0a8697/source.md
    title: "Meeting with Acme, weekly sync"
# verified: { by: "human:<name>", at: … }   ← added only once the human has reviewed the page
# stale_after: 2027-06-01T00:00:00+00:00    ← for perishable facts (a contract end, a price)
---
Prose body. Decision: ship in December.[^acme-sync-2026-11-04] See [Acme](/wiki/entities/01a1a5d1-2b40-7d10-8a77-c03f19e2b5a4.md).

[^acme-sync-2026-11-04]: Optional detail (section, timestamp).
```

- **`generated.at`**: update it on every significant change. **`generated.by`** always names the actual actor.
- **Links:** root-relative Markdown links (`/wiki/…md`, the path printed by `cortex new`), with the target page's title as the link text. A link always points to an existing page. For a person or a project still to write, create it with `cortex new` (a `status: draft` stub is enough), then link to it.
- **Reviewed page, then modified:** keep the `verified` entry (it is a past event), but switch back to `status: draft`. A `generated.at` later than `verified.at` means the page needs another review.
- **Deprecation:** a page contradicted by a more recent note is not deleted. It switches to `status: deprecated`, with a link at the top to what replaces it. A changed decision or a moved deadline is such a case: keep both, dated.
- **The `note`, when there is one, is copied into a callout** at the top of the body of the Source page only (never on a concept, entity or synthesis), with Obsidian's callout syntax and nothing else:
  ```markdown
  > [!note] Note personnelle
  > <the note, verbatim>
  ```

## From notes to pages

- **A meeting note** becomes a Source page for that meeting: date, participants, what was discussed, the decisions, and the action items with their owner and due date when the note gives them. Recurring people, projects and clients get an Entity page (update it if it exists), linked both ways: the Source page links to them, and each Entity page links back to the meeting.
- **A daily or personal note** (an appointment, something to remember) stays a dated Source page, linked to the Entity pages it concerns (a person, a place, a project). The date, time and place of an appointment are written in the page explicitly, in full (`2026-11-18 at 14:30`), never as "next Tuesday".
- **Docs and how-tos the human wrote** become Concept pages (how something works, a procedure, steps), citing the notes they come from.
- **A Synthesis page** gathers a recurring theme (a project's history, the open action items of a project) and only when several notes justify it. It cites them all; do not create one for a single note.
- A Source page keeps the substance of its note, in the human's words where wording matters (names, figures, decisions). It is a faithful record, not a commentary.

## `wiki/index.md`

This file has no frontmatter. It holds one section per type, and one bullet per page:

```markdown
# Index

## Entities
- [Acme](/wiki/entities/01a1a5d1-2b40-7c3e-9f21-5d8e0a4b7c12.md) — <description>

## …
```

## `wiki/log.jsonl` and `wiki/log.md`

`wiki/log.jsonl` is the journal: one JSON entry per line, chronological order, append-only. `wiki/log.md` is **generated** from it (readable in Obsidian, OKF reserved): the most recent entries come first, grouped by date. **You never write the journal by hand**: `cortex log add`.

```json
{"at": "2026-11-04T10:00:00+01:00", "kind": "ingest", "text": "created the weekly sync with Acme, updated Acme.", "sources": ["01a1a5c9-5e80-7075-ae13-aab03b0a8697"], "pages": ["wiki/entities/01a1a5d1-2b40-7c3e-9f21-5d8e0a4b7c12.md"]}
```

- `kind`: `add` | `ingest` | `query` | `lint` | `update`. `text`: one line of inline Markdown. `sources` (raw ids) and `pages` (`wiki/….md` paths) are optional and validated: pass them rather than copying them into the text.
- `cortex log add <kind> "<text>" [--source <id>]… [--page <path>]…` writes the entry with the current time and regenerates `log.md`. Put the text in double quotes, without `$` or backticks (single quotes if the text contains some).

## INGEST workflow

1. Read the raw note in full, `note` field included. For an image, describe it with your vision.
2. Look for related pages: start with 2 or 3 searches, `cortex search "<terms>" --limit 20`, on the note's title, the names it mentions (people, projects, clients) and its key terms, then read the pages found (no pipe, `head` or `grep`: the commands run alone, `--limit` shortens the output). Do not read `wiki/index.md`: it is a catalog for humans, too long to load.
3. **Present to the human**, in 5 to 10 lines, what the note brings (decisions, dates, action items), what contradicts existing pages, and the list of pages to create or modify. Wait for their approval or corrections.
4. Write:
   - the Source page, created by `cortex new Source "<title>"` (the CLI prints its path, then you fill in the file);
   - the updates to existing entities and concepts, or their creation with `cortex new Entity|Concept "<title>"` when nothing comes close;
   - the links, in both directions.
5. Switch the raw note to `status: compiled`, unless you were started by `cortex compile`, which does it after checking that a Source page cites the note.
6. Run `cortex index`. Add the **Ingest** entry to the journal: `cortex log add ingest "…" --source <id> --page wiki/…md` for every page touched (the **Add** entry is already there, written by `cortex add`).

In your answer, do not copy the pages back: summarize in one line per file touched.

**Started by `cortex compile --batch`:** the CLI has already created the Source page (type, title, status, `sources`, `generated`, note callout when there is a note) and gives you its path: keep those parts and write the rest: description and tags in the frontmatter, the record of the note and the links in the body, after the note callout. It also stamps `generated` on every page you touch, brings a new tag back to the tag in use it nearly duplicates, keeps at most `max_tags` tags on a page you create, links the Source page and the pages citing the note both ways, takes the note callout off any other page, runs `cortex index` and writes the Ingest journal entry: skip steps 5 and 6.

## QUERY workflow

1. Search the wiki with `cortex search "<terms>" --limit 20` (2 or 3 queries on the key terms of the question), pick the relevant pages and read them **in full**. Do not reason on excerpts. Do not read `wiki/index.md`.
2. If the wiki is not enough, search `raw/` (`cortex search "<terms>" --in raw`). An answer found only in `raw/` reveals a **gap**: suggest compiling that note.
3. Answer by citing the wiki pages, with their links. Tell apart what the notes say from what you infer.
4. If the answer has lasting value (the open action items of a project, a timeline), suggest storing it as a Synthesis page (`cortex new Synthesis "<title>"`), then the journal (`cortex log add query "…" --page wiki/….md`) and the index.

## LINT workflow

Run `cortex lint --json`. It reports:
- **errors** (exit code 1): invalid YAML, missing `type` or `description`, broken link, footnote without a `sources[]` entry, missing resource, duplicate raw id;
- **warnings**: orphan page, page modified since its review, `stale_after` passed, note `pending` for more than 7 days, compiled note that no Source page cites, likely duplicates (same title, same raw note), near-synonym tags, file name outside the configured naming;
- **info**: pages never reviewed.

What the CLI cannot see is up to you: **contradictions between pages** (a deadline that moved, a decision reversed, two spellings of one person).

Fix what is mechanical. **Propose** to the human what needs judgment (merge, deprecate, settle a contradiction). End with a **Lint** entry in the journal (`cortex log add lint "…"`).

## The `cortex` CLI

```
cortex add <file|url|-> [--note "why I keep this"] [--dry-run]       # → raw/, status: pending, Add entry in the journal; `-` reads the note from standard input
cortex inbox [--dry-run]                                             # add on inbox/ (urls.txt, files), then empties it
cortex search "<terms>" [--in wiki|raw] [--json] [--limit N]         # hybrid (words, title typos, meaning if configured), wiki first
cortex index                                                         # regenerates wiki/index.md and wiki/log.md
cortex new <Source|Concept|Entity|Synthesis> "<title>"               # creates the page (draft) per page_path, prints its path
cortex log [--limit N] [--json] [--kind k]                           # reads the journal, newest first
cortex log add <kind> "<text>" [--source <id>]… [--page <path>]…     # appends an entry to wiki/log.jsonl
cortex lint [--json]                                                 # mechanical checks
cortex compile <id…> | --pending [--batch]                           # runs an agent on INGEST
cortex ask "<question>" [--file] [--interactive]                     # runs an agent on QUERY
cortex schema [--write]                                              # prints this schema; --write rewrites the agent file
```

- `cortex add` is idempotent: content already present returns the existing id. A note captured with `cortex add -` has no URL: its `note` field is the human's one line of context.
- **`cortex compile`** runs one agent session **per note**, one after the other (one session per task, against context rot).
  - **By default the session is interactive**: you present your plan to the human before writing (rule 6).
  - **With `--batch`, nobody approves**: you write directly, and every page touched goes to `status: draft`, to be reviewed later.
  - It switches the status to `compiled` only if a Source page cites the note, then regenerates the index. It reports any file modified outside `wiki/`.
- **`cortex ask` is read-only.** `--file` allows storing the answer as a Synthesis page (in `draft`), with its journal entry; the index and `log.md` are then regenerated.
- **Agent file:** `cortex schema --write` rewrites this schema into `CLAUDE.md` or `AGENTS.md` (per the configured client) of the space.
  - **The agent is confined:** the whole repository is read-only except `wiki/` (an OS sandbox, or checks on every tool call, per the client). Your shell is limited to `cortex search|index|lint|new|log`. You never read another space.
