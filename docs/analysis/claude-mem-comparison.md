## 1. System Overviews

### Cortex

Cortex is a **Go-first, CLI-native, three-layer semantic memory system** designed for AI coding agents. It provides explicit memory management through both a rich CLI and an MCP server. Memory is stored locally in Gob format; embeddings are generated by a locally running Ollama instance, making the entire pipeline offline-capable and zero-cost.

| Property | Value |
|----------|-------|
| Language | Go 1.24+ |
| Binary | Single static binary (`cortex`) |
| Runtime deps at runtime | Ollama (local) |
| Storage | Gob (binary Go encoding) |
| Embedding provider | Ollama — `nomic-embed-text` (768 dim) |
| Search | Cosine similarity (in-memory index) |
| Interfaces | 17 CLI commands + 13 MCP tools (stdio / SSE) |
| Memory model | 3 explicit layers: working → episodic → semantic |
| Session management | Deterministic UUID v5 from git branch name |
| Open-source licence | — |

### Claude-Mem

Claude-Mem is a **Node.js plugin for Claude Code** that automatically captures tool usage during AI coding sessions and builds a searchable, compressed memory of what the agent has done. It is strongly oriented toward automatic, passive capture and aims to minimise the burden on users.

| Property | Value |
|----------|-------|
| Language | TypeScript / Node.js 18+ |
| Runtime | Bun (auto-installed) + Python uv (for Chroma) |
| Storage | SQLite (local, `~/.claude-mem/`) |
| Vector DB | Chroma (embedded) |
| Embedding provider | Claude API via Anthropic SDK |
| Search | Hybrid: SQLite FTS5 + Chroma semantic |
| Interfaces | MCP tools (4 tools) + Web viewer (port 37777) |
| Memory model | Flat: Sessions + Observations + Summaries |
| Session management | Derived from Claude Code session lifecycle hooks |
| Open-source licence | AGPL-3.0 (+ PolyForm NC for `ragtime/`) |

## 2. Architecture Comparison

### 2.1 High-Level Architecture

```
CORTEX
═══════
CLI / MCP
    └─→ Memory Service
           ├─→ Embedder (Ollama)
           ├─→ Storage (GobStorage)
           │       ├─→ memories.gob   (episodic + semantic)
           │       └─→ working/*.gob  (session-scoped)
           ├─→ Search (cosine similarity)
           └─→ Consolidation / Autoprune Services

CLAUDE-MEM
══════════
Lifecycle Hooks (SessionStart · PostToolUse · SessionEnd …)
    └─→ Worker Service (HTTP port 37777)
           ├─→ SQLite (sessions · observations · summaries)
           ├─→ Chroma (vector index)
           ├─→ Claude API (summarisation / embeddings)
           └─→ MCP Tools (search · timeline · get_observations)
               Web UI (browser at localhost:37777)
```

### 2.2 Design Philosophy

| Dimension | Cortex | Claude-Mem |
|-----------|--------|-----------|
| **Capture model** | Explicit (user or agent calls CLI/MCP) | Automatic (hooks fire on every tool use) |
| **Memory granularity** | User-defined (title + content + level) | Fine-grained (individual tool invocations) |
| **Summarisation** | Manual (consolidate command / MCP tool) | Automatic (Claude generates semantic summaries) |
| **Deduplication** | Explicit threshold (0.85 similarity) | Implicit (via Chroma similarity index) |
| **Lifecycle control** | Explicit (transfer, promote, delete) | Implicit (hooks manage state machine) |
| **Observability** | CLI stats, JSON output | Web UI + REST API |
| **Distribution** | Single binary, no cloud services | Multi-process: Bun worker + uv/Chroma |

## 3. Memory Model Comparison

### 3.1 Entity Models

**Cortex — `Memory`**

```go
type Memory struct {
    ID         string        // UUID
    Level      MemoryLevel   // working | episodic | semantic
    Title      string        // min 3 chars, human-readable
    Content    string        // min 10 chars, Markdown
    Tags       []string      // categorisation
    Embedding  []float64     // 768-dim vector
    Context    MemoryContext // SessionID, TaskID, Author, Source, RelatedMemories
    CreatedAt  time.Time
    UpdatedAt  time.Time
    MergedFrom []string      // lineage tracking after consolidation
    Obsolete   bool          // soft-delete flag
}
```

**Claude-Mem — three entity types**

| Entity | Fields | Purpose |
|--------|--------|---------|
| `Session` | id, project, start/end time, metadata | Groups observations |
| `Observation` | id, session_id, tool, input, output, timestamp | Raw tool trace |
| `Summary` | id, session_id, content, embedding | AI-compressed context |

### 3.2 Memory Hierarchy

| Aspect | Cortex | Claude-Mem |
|--------|--------|-----------|
| **Layers** | 3 explicit (working / episodic / semantic) | Flat (observation → summary) |
| **Promotion path** | working → episodic → semantic (intentional, user-driven) | Observation → Summary (automatic, AI-driven) |
| **Retention** | Configurable per level (working: session; episodic: 90 days; semantic: forever) | No explicit retention tiers |
| **Lineage** | `MergedFrom[]` tracks all source memory IDs | Observation IDs referenced in summaries |
| **Soft delete** | `Obsolete` flag (excluded from search, preserved for audit) | Not documented |
| **Rich metadata** | TaskID, SessionID, Author, Source, RelatedMemories | Session ID only |

### 3.3 Summary

Cortex's model is **richer and more explicit**: each memory carries full provenance, lifecycle metadata, and belongs to a distinct semantic tier. Claude-Mem's model is **simpler and more automatic**: it prioritises zero-effort capture over fine-grained control.

## 4. Storage & Search Comparison

### 4.1 Storage Backend

| Property | Cortex (GobStorage) | Claude-Mem (SQLite + Chroma) |
|----------|---------------------|------------------------------|
| **Format** | Binary Gob (Go-native) | SQLite rows + Chroma vectors |
| **Human-readable** | No (binary) | SQLite queryable; Chroma binary |
| **FTS (keyword search)** | No | SQLite FTS5 full-text index |
| **Vector storage** | Embedded field in Gob | Dedicated Chroma DB |
| **Thread safety** | `sync.RWMutex` | SQLite WAL mode |
| **Cross-language** | Go only | Language-agnostic (SQLite/Chroma) |
| **Performance ceiling** | ~10 k memories (in-memory index) | Scales to hundreds of thousands |
| **Zero-config** | Yes | Yes (auto-creates `~/.claude-mem/`) |
| **Pluggable** | Yes (`storage.Storage` interface) | No |

### 4.2 Search Capabilities

| Feature | Cortex | Claude-Mem | Gap |
|---------|--------|-----------|-----|
| **Semantic (vector) search** | ✅ Cosine similarity, 768-dim | ✅ Chroma vector search | — |
| **Keyword / FTS search** | ❌ | ✅ SQLite FTS5 | **Cortex missing** |
| **Hybrid (semantic + keyword)** | ❌ | ✅ BM25 + cosine combined | **Cortex missing** |
| **Date-range filter** | ❌ (filter by obsolete only) | ✅ (type + date + project) | **Cortex missing** |
| **Project/scope filter** | Tags (manual) | Project field | Cortex has tags |
| **Progressive disclosure** | ❌ | ✅ 3-layer (~10× token savings) | **Cortex missing** |
| **Result ranking** | Cosine score | Hybrid relevance | Comparable |
| **Top-K / min-score config** | ✅ Configurable | Not documented | Cortex richer |
| **Include obsolete flag** | ✅ | N/A | Cortex richer |

### 4.3 Search Complexity

| Operation | Cortex | Claude-Mem |
|-----------|--------|-----------|
| Get by ID | O(1) hash | O(1) SQLite PK |
| Semantic search | O(N·D) linear scan | O(log N) HNSW (Chroma) |
| Keyword search | O(N·C) content scan | O(log N) FTS5 inverted index |
| Combined | N/A | Parallel, merged |

### 5.3 Notable Cortex Advantages

- 3 **thinking/workflow** tools have no Claude-Mem equivalent: `cortex_review_session`, `cortex_think_about_task_completion`, `cortex_think_about_memory_maintenance`. These inject structured reflection prompts into the agent loop.
- 2 **decision-support** tools have no Claude-Mem equivalent: `cortex_choose_memory_layer`, `cortex_choose_working_consolidation`. They help agents decide where and what to store.
- `cortex_promote_memory` and `cortex_mark_obsolete` give fine-grained lifecycle control absent in Claude-Mem.

### 5.4 Notable Claude-Mem Advantages

- `timeline` tool: retrieve chronological context *around* a given observation — unique to Claude-Mem.
- Web UI: visual browsing, session timeline, statistics at `localhost:37777` — completely absent in Cortex.
- Token cost visibility: each disclosure layer reports its token overhead — enables cost-aware agents.

| **Automatic AI summarisation** | Medium — reduces storage and token overhead significantly | 🟡 Medium |
| **Timeline MCP tool** | Medium — chronological context is valuable for debugging chains | 🟡 Medium |
| **Web UI** | Medium — improves discoverability and debugging for non-CLI users | 🟡 Medium |
| **`<private>` tag support** | Medium — necessary for compliance-sensitive environments | 🟡 Medium |
| **Token cost visibility** | Low — useful for cost-optimisation but not blocking | 🟢 Low |
| **OpenClaw / chat integrations** | Low — niche use case, not core memory functionality | 🟢 Low |

### 9.2 Features Cortex Has That Claude-Mem Lacks

| Feature | Cortex Advantage |
|---------|-----------------|

## 10. Strategic Analysis

### 10.1 Core Differentiation

Cortex and Claude-Mem solve the same fundamental problem — persistent semantic memory for AI agents — but from opposite ends of the automation spectrum:

- **Claude-Mem** prioritises **zero-effort capture**: hooks into every tool use, injects context automatically, generates summaries via Claude, requires no deliberate memory management.
- **Cortex** prioritises **intentional, structured knowledge**: richer data model, explicit promotion paths, configurable deduplication, full export/import, single-binary deployment.

Neither approach is strictly superior. The ideal system would combine Claude-Mem's passive capture with Cortex's rich structure and explicit lifecycle control.

### 10.2 Recommended Strategic Posture

Rather than replicating Claude-Mem wholesale, Cortex should:

1. **Adopt** features that reduce friction without sacrificing control.
2. **Reject** features that conflict with Cortex's single-binary, offline-first design.
3. **Deepen** areas where Cortex already leads (lifecycle, reflection, metadata richness).

### 10.3 What to Adopt

| Feature | Rationale |
|---------|-----------|
| **FTS5 hybrid search** | Prerequisite for reliable exact-term retrieval; fundamentally missing from current Cortex |
| **Auto-summarisation MCP tool** | Can be offered as an opt-in tool (`cortex_summarise_working`), preserving user control |
| **Timeline MCP tool** | High-value pattern for debugging; simple to implement on top of existing history |
| **Privacy tags** | Required for enterprise adoption; low implementation cost |
| **Token-aware search** | Improves agent efficiency; surfaceable as optional search response field |
| **Pluggable SQLite backend** | Unlocks FTS5, better scaling, and cross-language access |

### 10.4 What Not to Adopt

| Feature | Reason to Skip |
|---------|---------------|
| **Fully automatic capture** | Reduces user control, generates noise; Cortex's explicit model is a feature, not a bug |
| **Automatic context injection on every prompt** | Risks injecting stale/irrelevant context; Cortex agents should remain deliberate |
| **Chroma as primary vector DB** | Adds a Python subprocess dependency; conflicts with single-binary goal |
| **Node.js / Bun runtime** | Architectural non-starter for a Go project |
| **Cloud embedding providers** | Conflicts with offline-first privacy posture |
